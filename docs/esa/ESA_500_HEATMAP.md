# How to read the ESA 500-card evidence heatmap

The [interactive evidence atlas](https://claimbound.github.io/claimbound-evidence/)
and its [static heatmap](../assets/esa_500_heatmap.svg) summarize the completed
ESA factory campaign without hiding the boundary of any individual card.

## What the axes mean

The map contains **25 rows x 20 columns = 500 cells**.

- A row is one selected official ESA mission landing page.
- A cell is one frozen ClaimBound source gate applied to that page.
- A column is a protocol position from `01` to `20`.

The columns must not be read as 20 universal scientific metrics. Issues
`#132`-`#135` use a standardized sequence of page-coverage gates. The first
batch, issue `#131`, predates that normalization and contains mission-specific
topics in those same positions. The interactive view therefore exposes the exact
topic and claim for every selected cell instead of substituting a misleading
cross-mission label.

## What the colors mean

| Color | Result status | Exact interpretation |
| --- | --- | --- |
| Green | `PASSED_UNDER_PROTOCOL` | The exact terms required by the frozen gate were present inside the selected source boundary. |
| Amber | `INSUFFICIENT_COVERAGE` | One or more required terms were absent from that source boundary. |

Green does not certify a mission, validate a scientific result, or imply ESA
endorsement. Amber does not say that a mission fact is false. Both colors report
only what the selected official page supported under one preregistered gate.

## The result

| Measure | Count |
| --- | ---: |
| Evidence cards | 500 |
| Official mission pages | 25 |
| Passed gates | 490 |
| Limited-coverage gates | 10 |
| Blocked runs | 0 |

The ten limited cells are unusually coherent: five mission landing pages omit
both the launch-site and launch-vehicle markers required by slots `08` and `09`.

| Mission | Limited slots | Missing page fields |
| --- | --- | --- |
| Gaia | `08`, `09` | Launch site, launch vehicle |
| ExoMars | `08`, `09` | Launch site, launch vehicle |
| Mars Express | `08`, `09` | Launch site, launch vehicle |
| Rosetta | `08`, `09` | Launch site, launch vehicle |
| Cluster | `08`, `09` | Launch site, launch vehicle |

This is a useful information-architecture result. It shows that most selected
landing pages expose broad mission and science descriptions consistently, while
some operational launch metadata requires a deeper source than the page chosen
for this campaign. ClaimBound preserves that distinction rather than widening
the search after seeing the result.

## How the interactive filters work

- **Batch** isolates one of the five 100-card GitHub issue batches.
- **Status** separates exact source matches from limited coverage.
- **Protocol slot** compares the same positional gate across the available rows.
- **Show only gaps** reduces the field to the ten amber records.
- Selecting a cell opens its exact protocol ID, topic, frozen claim, official
  source URL, access date, SHA-256 digest, missing patterns, JSON, and rendered
  evidence card.

The interface intentionally avoids a carousel or decorative card animation.
With 500 records, motion would reduce scanability. Small transitions are limited
to selection and filtering, and are removed when the operating system requests
reduced motion.

## Provenance and reproducibility

The atlas is generated by [`scripts/build_esa_factory_atlas.py`](../../scripts/build_esa_factory_atlas.py)
from the committed issue summaries, evidence cards, and registry. Generation
fails if a protocol is duplicated, a mission lacks one of the 20 slots, a card
is absent from the registry, a path is missing, or a status/source differs from
the registered evidence card.

Generated outputs:

- [`atlas-data.json`](atlas/atlas-data.json) - all 500 normalized records;
- [`atlas-data.js`](atlas/atlas-data.js) - the same data for an offline, fetch-free page;
- [`esa_500_heatmap.svg`](../assets/esa_500_heatmap.svg) - README-safe static view;
- [`index.html`](atlas/index.html) - dependency-free interactive atlas.

Rebuild and validate:

```bash
uv run python scripts/build_esa_factory_atlas.py
uv run claimbound validate-all
uv run --extra dev pytest -q
```

## Why the 500 cards matter

The campaign is not valuable because `500` is a large number. Its value is that
every record remains narrow, inspectable, and rerunnable at that scale:

1. It creates a public baseline for future source-drift comparisons.
2. It reveals systematic documentation gaps that one-card examples cannot show.
3. It tests whether generation, validation, registration, and presentation can
   scale without concealing non-passes.
4. It gives reviewers machine-readable data and direct paths back to every card.

The next analytically meaningful step is temporal: rerun the same frozen gates
and visualize which cells changed status or source hash. That would turn this
coverage map into a source-drift timeline without changing the original claims.
